# 6단계 성능 측정

2026-10-23 · 결과: [docs/reports/step-06.md](../reports/step-06.md) · 앞 단계: [1단계](step-01-environment.md) (GPU 비동기와 synchronize, 통합 메모리)

## 한 문장으로
모델 구성 5개를 따로 올려 쟀더니 텍스트는 146 ms로 GPU가 거의 놀고, 이미지는 장당 약 0.4 s로 GPU가 꽉 찼으며, 인코더를 다 올려도 RSS는 893 MB만 늘었지만 스왑은 1.2 GB 늘었다.

## 세미나용 1분 설명
같은 모델이라도 무엇을 넣느냐에 따라 병목이 완전히 다릅니다. 짧은 질의 두 개는 146 ms인데 GPU 사용률이 12%였습니다. 계산보다 준비 작업(토큰화, 커널 호출)이 더 오래 걸린다는 뜻으로, DB로 치면 쿼리 실행보다 커넥션 맺는 비용이 큰 상황입니다. 이럴 땐 여러 개를 모아 한 번에 보내는 배치가 효과적입니다. 반대로 이미지 5장은 GPU 99%에 2초로, 계산 자체가 병목이라 배치로 모아도 크게 줄지 않고 입력 수를 줄여야 합니다. 메모리도 재미있었는데, 모델 크기가 270M에서 740M으로 세 배 가까이 커져도 RSS는 1.7GB에서 2.6GB로만 늘었습니다. 기본 비용 1GB가 CUDA 자체였기 때문입니다. 그래서 공용 보드에서는 모델 프로세스를 여러 개 띄우는 것보다 하나에 인코더를 여럿 올리는 게 훨씬 쌉니다.

## 핵심 개념

### 두 번째 실행 값 (워밍업)
- 정의: 첫 실행에는 CUDA 커널 로드, 전처리기 초기화 같은 일회성 비용이 섞여 있어 안정 상태 지연은 두 번째부터 잰다.
- 비유: JVM 워밍업 전 첫 요청, 캐시가 빈 상태의 첫 쿼리(cold cache).
- 이 레포에서는: `src/bench.py:62-67` — 같은 입력을 두 번 encode하고 두 번째 값을 쓴다.
- 잘못하면: 오디오는 1회 3503 ms, 2회 354 ms로 10배 차이. 첫 값으로 표를 채우면 오디오가 가장 느린 구성으로 잘못 기록된다.

### 계산 병목 vs 오버헤드 병목
- 정의: GPU 사용률이 낮은데 느리면 오버헤드(토큰화, 파이썬, 커널 호출)가, 사용률이 100%면 계산이 병목이다.
- 비유: DB 응답이 느릴 때 CPU가 놀면 커넥션·네트워크 왕복을, CPU가 꽉 차면 쿼리 자체를 의심하는 것.
- 이 레포에서는: `docs/reports/step-06.md` — 텍스트 12% / 이미지·영상 99%.
- 잘못하면: 텍스트 지연을 줄이려고 더 큰 GPU를 사거나, 이미지 지연을 줄이려고 배치만 키우는 엉뚱한 최적화를 한다.

### 고정 비용 vs 모델 크기 비용
- 정의: GPU 프로세스는 모델과 별개로 CUDA 컨텍스트·라이브러리 메모리(여기서 약 1.1 GB)를 먼저 쓴다.
- 비유: 커넥션 하나마다 붙는 고정 메모리. 커넥션 풀을 여러 개 만들면 고정 비용이 곱해진다.
- 이 레포에서는: `docs/reports/step-06.md` 관찰 — 텍스트 1680 MB → 전체 2573 MB(+893 MB).
- 잘못하면: 팀원 넷이 각자 텍스트 모델을 띄우면 4 × 1.7 GB = 6.8 GB로 보드가 끝난다. 한 프로세스(추론 서버)에 모으고 API로 부른다.

## 비교
- 무슨 문제: 공용 8GB 보드에서 어떤 구성을 올릴 수 있는지, 어디가 느린지 숫자로 정하기.
- 대안 1 — tegrastats를 보며 손으로 기록(원문): 도구가 단순하다.
  - 이 대안을 썼다면: 최대값을 눈으로 놓치고, 구성마다 입력·동기화 방식이 달라 비교가 흐려진다.
- 대안 2 — PyTorch 프로파일러(torch.profiler): 연산 단위로 어디가 느린지 보인다. 대신 오버헤드가 커서 지연 자체가 바뀌고 결과가 무겁다. "어디를 최적화할지" 단계에 쓰는 도구.
- 이 방식의 약점: 반복 2회라 분산을 모른다. 같은 보드의 다른 프로세스(센서 추론 서비스) 부하를 통제하지 못했다. 자물쇠를 잡아 팀원을 막는다.
- 실무 Use Case: 추론 서버 배포 전 용량 계획. 모델 구성별 RSS·GPU 메모리·p50/p95 지연을 같은 스크립트로 재고, 인스턴스당 동시 처리 수와 필요한 인스턴스 수를 정한다.

## 실제로 겪은 문제 → 원인 → 해결
- 측정 중 팀원이 "잠금" 메시지로 카메라 앱을 못 켬 → 측정도 `practice.sh` 자물쇠를 잡음(보드 전체 하나) → 잡기 전에 팀에 알리기로 함.

## 일부러 망가뜨려 볼 실험
1. **synchronize 빼기** — 1단계에서 실제로 함: 동기화 없이 0.08 ms, 있으면 12.8 ms. `src/bench.py`의 `torch.cuda.synchronize()` 두 줄을 빼면 이미지 지연이 실제보다 짧게 찍힐 것이다(이번엔 미실행).
2. **배치 크기 1 vs 5** (해 볼 것): `model.encode(..., batch_size=1)`로 이미지 5장을 넣어 2082 ms와 비교. 예상: 텍스트는 배치가 크게 효과 있고(오버헤드 병목), 이미지는 효과가 작다(계산 병목). 자물쇠를 잡아야 하므로 팀원 카메라 사용이 끝난 뒤에.
