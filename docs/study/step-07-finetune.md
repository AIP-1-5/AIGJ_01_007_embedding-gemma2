# 7단계 도메인 미세 조정

2026-10-23 · 결과: [docs/reports/step-07.md](../reports/step-07.md) · 앞 단계: [3단계](step-03-text.md) (임베딩 검색, 프롬프트, Matryoshka)

## 한 문장으로
강의실 운영 질의-문서 300쌍으로 맥에서 3분 학습해 도메인 검색 acc@1을 0.817 → 0.867로 올렸지만, 3단계 일반 질의 하나가 256·128차원에서 오답으로 뒤집혔고 점수 척도가 크게 바뀌었다.

## 세미나용 1분 설명
기본 임베딩 모델은 인터넷 전체 글로 배운 "일반인"이라, 우리 강의실 규칙처럼 좁은 분야에서는 비슷한 문서끼리 헷갈립니다. 미세 조정은 "이 질문엔 이 문서가 답"이라는 쌍을 보여 주며 지도를 조금 고쳐 그리는 일입니다. 방식이 재미있는데, 한 배치의 질문 8개와 정답 문서 8개를 놓고 "자기 짝은 가깝게, 남의 짝은 멀게" 당깁니다. 오답을 따로 만들 필요 없이 같은 배치의 다른 문서가 오답 역할을 합니다. 검색 엔진으로 치면 동의어 사전을 손으로 넣는 대신, 클릭 로그로 랭킹을 튜닝하는 것과 비슷합니다. 결과는 도메인 질의 60개 중 3개를 더 맞혔습니다. 하지만 공짜는 아니었습니다. 학습에 없던 질문 하나가 오히려 틀렸고, 유사도 점수 크기가 0.7대에서 0.2~0.5대로 바뀌어 "0.6 넘으면 일치" 같은 기준은 다시 정해야 합니다. 인덱스를 바꾸면 쿼리 플랜이 바뀌듯, 모델을 바꾸면 임계값과 기존 벡터를 다 다시 봐야 합니다.

## 핵심 개념

### 배치 내 오답 학습 (MultipleNegativesRankingLoss)
- 정의: 배치 안의 (질의, 정답 문서) 쌍에서, 각 질의의 정답은 자기 문서이고 나머지 문서는 모두 오답으로 쓴다.
- 비유: 8명에게 각자 자기 택배를 찾게 하면, 나머지 7개 택배는 저절로 "남의 것"이 된다. 오답 데이터를 따로 모을 필요가 없다.
- 이 레포에서는: `src/train_ft.py:53-54` — `MultipleNegativesRankingLoss`를 `MatryoshkaLoss`로 감싼다. `src/train_ft.py:63`의 `NO_DUPLICATES`는 같은 문서가 한 배치에 두 번 들어가 "정답이 오답"이 되는 것을 막는다.
- 잘못하면: 우리 데이터는 문서 하나에 질의 3개라, 중복 방지가 없으면 같은 문서가 한 배치에서 정답이자 오답이 된다. 배치를 4로 줄이면 오답 수가 줄어 학습 효과가 작아진다(원문).

### 평가 세트와 설정 고르기의 분리
- 정의: 평가 데이터는 마지막 성적표로만 쓰고, epoch·lr 같은 설정은 학습 데이터에서 떼어 낸 검증 세트로 고른다.
- 비유: 시험 문제를 보고 공부 범위를 정하면 점수는 오르지만 실력은 그대로. 성능 테스트 결과를 보고 테스트 케이스에 맞춘 캐시를 넣는 것과 같다.
- 이 레포에서는: `docs/mac-training.md` 3번, 팀 규칙. 원문은 "과적합이면 epoch·lr 낮추기"라고 하지만 하지 않았다.
- 잘못하면: 0.867 같은 숫자를 믿을 수 없게 된다. 60쌍에서는 질의 1개가 0.017이라 몇 번만 고르면 쉽게 "개선"이 만들어진다.

### 점수 척도(캘리브레이션) 변화
- 정의: 학습이 순위만 맞추도록 벡터를 옮기면, 유사도 값의 절대 크기와 분포가 바뀐다.
- 비유: 인덱스를 바꾸면 결과는 같아도 쿼리 비용 숫자가 달라지는 것. 또는 시험 난이도가 바뀌면 60점의 의미가 달라지는 것.
- 이 레포에서는: `docs/reports/step-07.md` 관찰 — 3단계 질의 1 최고 점수 0.717 → 0.264.
- 잘못하면: 8단계 재라벨·10단계 재확인처럼 "유사도 0.x 이상이면 같은 물체"로 쓰는 곳에서 모델만 바꾸면 전부 판정 실패로 바뀐다.

### 모델 교체 = 전체 재색인
- 정의: 문서 벡터와 질의 벡터는 같은 모델로 만들어야 비교된다. 모델이 바뀌면 저장된 문서 벡터를 모두 다시 만든다.
- 비유: DB 문자셋·정렬 규칙(collation)을 바꾸면 인덱스를 다시 만드는 것.
- 이 레포에서는: `src/eg2.py:15` — `EG2_MODEL`로 모델을 바꾸면 그 모델로 문서와 질의를 모두 다시 인코딩한다.
- 잘못하면: 옛 모델로 만든 문서 벡터 + 새 모델 질의 벡터 → 에러 없이 엉뚱한 결과.

## 비교
- 무슨 문제: 좁은 도메인(강의실 운영 규칙)에서 비슷한 문서끼리 헷갈리는 검색을 고치기.
- 대안 1 — 미세 조정 없이 하이브리드 검색(BM25 + 임베딩): "에이전트", "승인" 같은 핵심어가 겹치는 질의는 BM25가 잡는다.
  - 이 대안을 썼다면: "에이전트가 추천하면 바로 환기가 켜지나요"처럼 키워드가 문서와 다른 질의는 여전히 틀린다. 대신 모델·재색인·임계값 재조정 비용이 없다.
- 대안 2 — 재정렬기(cross-encoder) 추가: 상위 10개만 질의와 문서를 함께 보고 다시 순위를 매긴다. 정확하지만 질의마다 10번 추론이라 보드에서는 지연이 커진다.
- 이 방식의 약점: 일반 질의 성능이 흔들릴 수 있고(이번에 1개 뒤집힘), 점수 척도가 바뀌며, 모델 하나를 더 관리하고 재색인해야 한다. 텍스트 전용이라 이미지·음성 검색에는 쓸 수 없다.
- 실무 Use Case: 사내 헬프데스크 FAQ 검색. 실제 문의 로그(질의 → 해결 문서 클릭)로 쌍을 만들어 분기마다 미세 조정하고, 배포 전에 고정 평가 세트와 일반 질의 세트 두 개로 회귀 테스트한다.

## 실제로 겪은 문제 → 원인 → 해결
- 원문이 제공한다는 `train.jsonl`/`eval.jsonl`이 없음 → 원문 저장소에 README만 있음 → 원문 규격대로 직접 작성(한계는 보고서에).
- 맥 Python 3.9.6, `PIL`/`Torchvision` 없음, `pyarrow requires NumPy 2.0` → 맥 환경 차이와 pyctcdecode의 numpy<2 고정 → uv로 3.12, 전체 extra, pyctcdecode 제거(`docs/mac-training.md`).
- 맥 원격 로그인이 꺼져 있어 보드에서 학습 지시 불가 → 원격 로그인 + 보드 공개키 등록.
- 일반 질의 1개가 256·128차원에서 오답 → 학습 후 경계 이동. 팀 규칙대로 설정을 다시 고르지 않고 그대로 기록.

## 일부러 망가뜨려 볼 실험
1. **dtype만 바꿔 같은 평가** — 실제: 기준 모델이 맥 float32 0.833, 보드 bfloat16 0.817. 차이 0.001이던 질의 하나가 뒤집혔다. "평가 점수 차 0.016"은 학습 효과가 아니어도 생긴다 → 비교는 같은 장비·dtype에서만.
2. **배치 2로 학습** (맥에서 해 볼 것): `~/eg2-mac/bin/python src/train_ft.py --batch 2 --accum 8 --out models/eg2-b2` — 예상: 배치 안 오답이 1개뿐이라 개선 폭이 작아진다. 평가는 보고만 하고 이 결과로 설정을 고르지 않는다. (이번엔 미실행)

<details><summary>2. 왜: 평가 결과를 보고 epoch·lr을 다시 고르면 안 되는 이유는?</summary>평가 세트에 맞춘 설정을 고르는 셈이라 보고한 점수가 실제 일반화 성능보다 높게 나온다. 60쌍이면 질의 1개가 0.017이라 몇 번 시도만으로 "개선"이 생긴다. 설정은 학습 데이터에서 뗀 검증 세트로 고른다.</details>
<details><summary>3. 트레이드오프: 미세 조정과 하이브리드 검색(BM25 + 임베딩) 중 무엇을 먼저 하나?</summary>보통 하이브리드 먼저. 모델·재색인·임계값 재조정 비용이 없고 일반 성능도 안 흔들린다. 키워드가 안 겹치는 도메인 질의가 계속 틀리고 질의 로그가 충분히 쌓였을 때 미세 조정을 한다.</details>
