# 9단계 사람 동작 인식

2026-10-26 · 결과: [docs/reports/step-09.md](../reports/step-09.md) · 앞 단계: [8단계](step-08-object-search.md) (검출과 추적, 생산자-소비자), [7단계](step-07-finetune.md) (평가 세트와 설정 고르기)

> 9-1·9-2·9-5·9-3(동작)·9-6을 실행한 뒤 쓴 노트다. 악수와 행동 녹화 2종은 10단계 때 카메라 2대·팀원과 함께 한다.

## 한 문장으로
관절 17개로 만세·한팔들기를 규칙으로 판정했더니, 프레임마다 판정하면(raw) 실제 12번 동작에 이벤트가 44번 생겼다. 0.6초 다수결과 1.5초 손목 궤적을 보게 하자(smooth) 12번으로 맞았고 손 흔들기도 0 → 3회로 잡혔다. 하지만 옆모습은 시간을 더 봐도 고쳐지지 않았다. 규칙 대신 학습하려고 동작 4종을 녹화해 맥에서 GRU를 학습했는데, 저장된 모델이 거의 학습 전 상태(검증 정확도 0.358)였다. 앱은 확률 0.7 미만이면 모델 판정을 버리고 규칙으로 돌아가므로 아무 일도 일어나지 않았다.

## 세미나용 1분 설명
포즈 모델은 사람마다 코, 어깨, 손목 같은 관절 17개의 좌표를 줍니다. "손목이 어깨보다 위면 손을 든 것"처럼 규칙을 쓰면 동작 인식기가 바로 만들어지지만, 사진 한 장씩 판정하면 관절이 조금만 흔들려도 라벨이 깜빡여서 동작 12번에 이벤트가 44번 찍혔습니다. 그래서 최근 0.6초 판정 중 60% 이상인 것만 믿게 했습니다. CPU가 한 번 튀었다고 알람을 보내지 않고 "5분 중 3분 이상"일 때 보내는 것과 같습니다. 손 흔들기는 한 장면으로는 손을 든 것과 같아서 1.5초 동안 손목이 몇 번 방향을 바꿨는지 셉니다. 이것으로 12번, 손 흔들기 3번이 맞았습니다. 그래도 옆으로 서면 팔이 가려져 놓쳤고, 서 있기만 해도 "지나감"과 "머무름"이 오갔습니다. 규칙의 기준값이 현장과 어긋나는 것입니다. 그래서 동작을 녹화해 GRU에 학습시켰는데, 보드에서 다시 평가해 보니 저장된 가중치가 초기값과 거의 같았습니다. 그래도 앱은 "확신 없으면 규칙으로" 설계라 망가지지 않았습니다. 새 모델을 배포할 때 이전 경로를 남겨 두는 폴백과 같습니다.

## 핵심 개념

### 시간 창 다수결 (디바운싱)
- 정의: 최근 N초의 판정 중 가장 많은 라벨이 일정 비율 이상일 때만 상태를 바꾸고, 아니면 이전 상태를 유지한다.
- 비유: 알람의 지속 조건(Prometheus `for: 5m`), 키보드 입력 디바운싱. 이벤트가 아니라 상태로 생각한다.
- 이 레포에서는: `src/pose_app.py:233-234` — `majority(st["raw"], now, SMOOTH_S)`가 60% 이상이면 확정, 아니면 `st["label"]` 유지. `src/pose_app.py:55` `SMOOTH_S = 0.6`. 악수도 같은 방식(`src/pose_app.py:309-310`).
- 잘못하면: 창이 짧으면 깜빡임이 남고(raw 44회), 길면 늦고 짧은 동작을 놓친다(합성 실험: 2.0초 창에서 1초 동작 0회). 창을 평가 결과로 고르면 [7단계](step-07-finetune.md)의 "평가로 설정 고르기"가 된다.

### 한 프레임으로는 알 수 없는 동작
- 정의: 손 흔들기처럼 "변화"로 정의되는 동작은 한 장면에 정보가 없다. 시간 축 특징(방향 전환 횟수)이 필요하다.
- 비유: 로그 한 줄로는 재시도 폭주를 알 수 없고, 같은 요청 ID가 몇 초 안에 몇 번 나왔는지 세야 한다.
- 이 레포에서는: `src/pose_app.py:223` — 손을 든 동안 손목 x를 어깨 너비로 정규화해 쌓는다. `src/pose_app.py:115` `is_wave` — 0.15 이상 움직임에서 방향이 2번 이상 바뀌면 손 흔들기. `src/pose_app.py:236`에서 한팔들기일 때만 검사.
- 잘못하면: raw에서 손 흔들기 0회, 깜빡이는 한팔들기 16회. 9-3 녹화에서는 사용자가 어깨 높이 이하에서 흔들어(손목이 어깨 위 7%) 규칙은 "손을 든 상태"부터 인정하지 않는다.

### 어깨 너비 정규화와 그 한계
- 정의: 좌표를 어깨 중심 원점, 어깨 너비 1로 바꿔 카메라 거리와 무관하게 비교한다. 속도도 어깨 너비/초.
- 비유: 지표를 절대값 대신 "평소 대비 비율"로 보는 것. 분모가 흔들리면 비율 전체가 흔들린다.
- 이 레포에서는: `src/pose_model.py:24-30` `body` — 어깨 너비 최소 20px(`:29`). `src/pose_app.py:104` `pose_label`은 손목이 어깨선보다 `0.3 * sw` 위인지, `src/pose_app.py:60` `MOVE_TH = 0.5`는 이동 판정 속도.
- 잘못하면: 옆으로 서면 분모가 작아지고 반대쪽 손목이 가려져 만세를 놓친다(smooth 3회 중 1회). 9-5에서는 서 있는 동안 작은 흔들림이 비율로 커져 머무름 ↔ 지나감이 1~4초마다 바뀌었다(추정).

### 추적 ID가 사람의 단위, 요약은 퇴장 때
- 정의: 상태(다수결 기록, 손목 궤적, 체류·정면 시간)는 추적 ID별로 쌓고, 3초 넘게 안 보이면 그 사람의 최고 단계 패턴을 요약으로 남긴다.
- 비유: 웹 세션. 세션 타임아웃이 나야 "이번 방문 요약"(체류 시간, 본 페이지)이 집계된다.
- 이 레포에서는: `src/pose_app.py:205` `update_person`, `src/pose_app.py:131` `behavior`(최근 15초로 패턴 판정), `src/pose_app.py:169` `close_track`(요약), `src/pose_app.py:65` `BEH_RANK`(관심 있음 > 힐끗 봄 > 머무름 > 지나감).
- 잘못하면: 9-5 1차는 사용자가 화면을 안 떠나 시나리오 12번이 한 세션이 됐고, 2차도 12번에 요약 7개였다. 행동 모델의 라벨 이름이 `BEH_RANK` 키와 다르면(영문 파일 이름) 최종 패턴 순위가 무너진다 → 녹화 파일을 한글 이름으로 정했다.

### 윈도 시퀀스 분류 (GRU)
- 정의: 프레임 특징 53개(정규화 좌표 34 + 관절 신뢰도 17 + 정면 점수 + 속도)를 30프레임(약 2초) 윈도로 묶어 GRU가 윈도 전체에 라벨 하나를 붙인다.
- 비유: 로그 한 줄이 아니라 2초 분량 로그 묶음을 보고 "이건 로그인 시도 폭주"라고 분류하는 이상 탐지 모델.
- 이 레포에서는: `src/pose_model.py:52` `PoseGRU`, `src/pose_model.py:45` `frame_features`. 앱은 5프레임마다 최근 30개로 추론한다(`src/pose_app.py:240`). 학습은 맥에서만(`src/train_pose.py`).
- 잘못하면: 파일 이름이 곧 정답이라, 녹화 중 화면에 다른 동작이나 다른 사람이 섞이면 그대로 틀린 정답이 된다. `idle` 없이 학습하면 모든 자세를 어떤 동작으로든 분류한다(원문).

### 시간순 분할과 학습·서빙 분포 차이
- 정의: 연속된 녹화를 무작위로 나누면 거의 같은 프레임이 학습과 검증에 함께 들어간다(누수). 그래서 각 녹화의 앞 80%를 학습, 뒤 20%를 검증으로 쓴다. 또 서빙(실제 사용) 환경이 학습 녹화와 다르면 검증 점수는 의미가 없다.
- 비유: 어제 로그로 학습하고 오늘 로그로 검증하는 것. 그리고 개발 DB 통계로 잡은 쿼리 플랜이 운영 DB에서 엉망이 되는 것.
- 이 레포에서는: `src/train_pose.py:68` `cut`, 보드 재평가 `src/eval_pose.py`(같은 분할을 다시 만든다). 카메라 위치가 다른 1차 녹화(`data/action/_trial1/`)는 전부 `arms_crossed`로 분류됐다.
- 잘못하면: 무작위 분할이면 검증 점수가 부풀려진다. 카메라를 옮기면(내려다봄, 손목·엉덩이 안 보임) 모델을 다시 녹화·학습해야 한다.

### 최고 검증 epoch 저장과 확신 기준 폴백
- 정의: 학습 중 검증 정확도가 가장 높은 epoch의 가중치를 저장하고, 앱은 모델 확률이 0.7 이상일 때만 모델 판정을 쓴다.
- 비유: 카나리 배포에서 지표가 가장 좋았던 버전을 고르고, 새 경로가 확신 없으면 기존 경로로 돌리는 폴백.
- 이 레포에서는: `src/train_pose.py:98-99` best 저장, `src/pose_app.py:61` `ML_TH = 0.7`, `src/pose_app.py:245` 미만이면 `None` → 규칙 판정 유지.
- 잘못하면: 검증 세트가 작고(라벨당 연속 구간 하나, 151윈도) 고르는 기준이 곧 보고 점수라, 초반 epoch이 "최고"로 뽑히면 거의 학습 안 된 모델이 저장될 수 있다. 이번 `action.pt`는 가중치 평균 절댓값이 초기값 수준(약 0.06), 정확도 0.358이었다(원인은 맥 로그로 확인 필요, 추정). 폴백 덕분에 앱은 규칙으로 계속 동작했다.

## 비교
- 무슨 문제: 관절 좌표의 프레임별 잡음, 시간으로만 정의되는 동작, 현장마다 어긋나는 기준값 때문에 규칙 판정이 깜빡이고 놓친다.
- 대안 1 — 관절 좌표 평활화(이동 평균, 칼만 필터): 깜빡임은 줄지만 판정 경계 근처에서는 여전히 오가고, 손 흔들기처럼 빠른 움직임이 지워진다.
- 대안 2 — 히스테리시스(올릴 때와 내릴 때 기준 분리): 가장 싸고 지연이 없지만 조정할 값이 늘고 시간 패턴은 따로 짜야 한다. 9-5 머무름 ↔ 지나감 반복에는 효과가 클 것이다(미실험).
- 대안 3 — 시퀀스 모델(9-6 GRU): 박수·팔짱처럼 규칙으로 쓰기 어려운 동작도 녹화만 하면 추가된다. 대신 녹화 품질·카메라 위치에 묶이고, 학습이 잘못돼도 겉으로는 티가 안 난다(이번 경우). 평가 파이프라인과 학습 로그가 같이 있어야 믿을 수 있다.
- 이 방식(다수결 + 손목 궤적 + 확신 기준 폴백)의 약점: 0.3~0.6초 지연, 옆모습·가림은 못 고침, 동작마다 규칙을 사람이 써야 함.
- 실무 Use Case: 매장 디지털 사이니지 앞 관심도 측정. "멈춰서 3초 이상 정면"을 관심으로 세고, 사람 단위 요약(체류, 정면 시간)만 저장해 영상은 남기지 않는다. 설치 위치가 바뀌면 기준값과 모델을 다시 검증한다.

## 실제로 겪은 문제 → 원인 → 해결
- 9-5 1차에서 요약 2개 → 카메라가 책상 위 1m라 사용자가 화면을 안 떠남 → 카메라를 눈높이 수평으로 옮겨 2차. 2차도 요약 7개(시도 12) → 시도 사이 화면 밖으로 3초 넘게 안 나감 → 부분 측정으로 기록(사용자 결정).
- 1차 동작 녹화에서 엉덩이 관절 0%, wave에 손 든 프레임 0 → 카메라가 내려다보는 위치 → 카메라를 옮겨 재녹화, 1차는 `data/action/_trial1/`로 분리.
- `action.pt` 정확도 0.358, 확률 전부 0.7 미만 → 저장된 가중치가 초기값 수준(맥 출력 미확인) → 보드 평가 스크립트를 만들고 맥 학습 로그를 남기도록 안내(`docs/mac-training.md`). 미해결.
- 앱 재시작 대기 루프가 끝나지 않음 → `pgrep -f pose_app.py`가 그 문자열을 담은 내 셸 명령과 일치 → 시간 제한 있는 대기로 바꿈(앱 문제 아님).

## 일부러 망가뜨려 볼 실험
1. **`SMOOTH_S`를 0.1과 2.0으로** — 합성 데이터로 실행(15 fps, 기본 자세 3초 뒤 동작, 4프레임 중 1프레임 손목이 어깨선으로 떨어지는 잡음):

   | | 잡음 섞인 3초 한팔들기 | 1초 한팔들기 | 0.4초 한팔들기 |
   |---|---|---|---|
   | raw | 11회 | 1회 | 1회 |
   | `SMOOTH_S` 0.1 | 1회, 지연 0.13 s | 1회, 0.07 s | 1회, 0.07 s |
   | 0.6 (원문) | 1회, 0.47 s | 1회, 0.33 s | 1회, 0.33 s |
   | 2.0 | 1회, 1.67 s | **0회** | **0회** |

   2.0은 예상대로 늦고 짧은 동작을 놓쳤다. 0.1이 깜빡이지 않은 것은 예상과 달랐다. 창 안에 프레임이 2개뿐이라 "1 : 1"이면 60%를 못 넘어 이전 라벨을 유지하기 때문이다. 잡음이 2프레임 연속이면 0.1도 깜빡일 것이다(미실행).
2. **다른 카메라 위치의 녹화로 모델 평가** — 실제: 1차 녹화(내려다봄)를 `src/eval_pose.py --extra data/action/_trial1/*.csv`로 넣자 clap·idle·wave 256윈도가 거의 전부 `arms_crossed`. 다만 이번 모델은 거의 학습 전 상태라, 제대로 학습된 모델로 다시 해야 "분포 차이" 효과만 볼 수 있다.

<details><summary>2. 왜: GRU 학습 데이터를 무작위가 아니라 시간순(앞 80% / 뒤 20%)으로 나누는 이유는?</summary>15 fps 녹화의 이웃 프레임은 거의 같다. 무작위로 나누면 같은 순간의 윈도가 학습과 검증에 함께 들어가 검증 점수가 부풀려진다(누수). 시간순으로 나누면 "조금 뒤의 처음 보는 구간"을 맞히는지 본다.</details>
<details><summary>3. 트레이드오프: 규칙(다수결 + 손목 궤적)과 GRU 중 무엇을 기본으로 두나?</summary>규칙은 설명 가능하고 데이터가 필요 없지만 동작마다 손으로 쓰고 현장 기준값이 어긋난다. GRU는 새 동작을 녹화만으로 추가하지만 녹화 환경에 묶이고 잘못 학습돼도 티가 안 난다. 규칙을 기본으로 두고 모델이 확신할 때만(0.7 이상) 덮어쓰는 지금 구조가 안전하다.</details>
<details><summary>4. 장애 상황: 새 모델을 배포했는데 화면에 모델 라벨(clap, arms_crossed)이 한 번도 안 뜬다. 무엇부터 보나?</summary>모델 확률이 `ML_TH`(0.7)를 넘는지 본다. 이번엔 전부 미만이라 앱이 규칙으로 폴백했다. 그다음 보드에서 같은 검증 분할로 재평가(정확도 0.358)하고, 가중치 크기가 초기값 수준인지, 학습 로그의 epoch별 val acc가 초반에 최고였는지 확인한다. 카메라 위치가 녹화 때와 같은지도 본다.</details>
<details><summary>5. 내 프로젝트 적용: 시계열 센서 이상 알림에 같은 원리를 쓴다면?</summary>한 번 튄 값으로 알림을 보내지 않고, 최근 N분 판정 중 일정 비율 이상이 이상일 때만 상태를 바꾼다. 학습 모델을 붙이면 시간순 분할로 평가하고, 확신이 낮으면 규칙 기반 판정으로 폴백하며, 센서 설치 위치가 바뀌면 다시 검증한다.</details>

> 💡 아이디어: 규칙 판정과 모델 판정이 어긋나는 구간만 모아 사람이 정답을 달면, 적은 녹화로 9-6 학습 데이터를 늘리고 동시에 잘못 학습된 모델을 일찍 잡을 수 있다.
