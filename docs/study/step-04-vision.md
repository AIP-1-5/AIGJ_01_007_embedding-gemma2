# 4단계 영상 테스트

2026-10-23 · 결과: [docs/reports/step-04.md](../reports/step-04.md) · 앞 단계: [5단계](step-05-audio.md) (멀티모달 공유 벡터 공간), [7단계](step-07-finetune.md) (hubness)

## 한 문장으로
웹캠으로 강의실 사진 5장과 10초 영상을 찍어 텍스트로 검색했더니 사물함·모니터·화이트보드는 맞혔지만, 모든 게 다 담긴 넓은 사진 한 장이 "빈 강의실"과 "수업 듣는 모습"까지 1위를 가져갔다.

## 세미나용 1분 설명
텍스트와 이미지를 같은 지도 위에 올려 두면 "사물함"이라는 글자로 사물함 사진을 찾을 수 있습니다. 이번에 진짜 강의실을 찍어 해 보니, 사물함처럼 한 가지만 크게 찍힌 사진은 0.1 차이로 확실히 찾았습니다. 그런데 스크린, 화이트보드, 모니터, 사람이 한 장에 다 들어간 넓은 사진은 질의 5개 중 3개에서 1위였습니다. 검색 엔진에서 모든 키워드가 다 들어간 긴 문서가 어떤 검색에도 걸리는 것과 같습니다. 그래서 실제 서비스에서는 사진 한 장을 통째로 색인하기보다 물체 단위로 잘라 색인하는데, 그게 바로 8단계(YOLO로 잘라 낸 뒤 임베딩)입니다. 영상은 초당 한 장씩 뽑아 하나의 벡터로 만들고, 모니터가 가득 찬 영상은 "컴퓨터 모니터 화면" 질의와 가장 가까웠습니다.

## 핵심 개념

### 장면 단위 임베딩의 한계 (넓은 사진 = 허브)
- 정의: 이미지 하나를 벡터 하나로 요약하면, 여러 물체가 섞인 장면은 "평균적인" 위치에 놓여 많은 질의와 적당히 가까워진다.
- 비유: 전문 검색에서 키워드가 다 들어간 긴 문서가 모든 검색 상위에 뜨는 것. 그래서 문서를 문단(청크)으로 잘라 색인한다.
- 이 레포에서는: `docs/reports/step-04.md` 관찰 — whiteboard.jpg가 질의 3개 1위, 2개 2위.
- 잘못하면: "사람이 있는 장면 찾기" 같은 기능이 넓은 사진만 계속 돌려준다. 8단계처럼 물체를 잘라(crop) 색인해야 한다.

### 영상 = 프레임 샘플링 + 하나의 벡터
- 정의: 영상을 초당 1장(모델 기본)으로 뽑아 인코더에 넣고 영상 전체를 벡터 하나로 만든다.
- 비유: 로그 전체 대신 1초 간격 샘플로 요약 통계를 만드는 것. 짧은 이벤트는 놓칠 수 있다.
- 이 레포에서는: `src/test_vision.py:29-36` — PyAV로 프레임 번호 기준 15장마다 1장(15 fps → 1 fps).
- 잘못하면: 샘플링이 빠지면 151프레임이 다 들어가 지연이 4배(7.6~9.2 s → 2.0 s). 반대로 너무 듬성하면 순간 장면을 놓친다.

### 디코더 의존성 (라이브러리 버전 사슬)
- 정의: 모델 라이브러리 → 영상 디코더(torchcodec) → 시스템 FFmpeg 공유 라이브러리(libavcodec, libswscale …)가 버전까지 맞아야 영상이 열린다.
- 비유: JDBC 드라이버가 OS의 네이티브 라이브러리(.so)를 요구하는데 서버에 없는 것.
- 이 레포에서는: `src/test_vision.py:39-46` — 경로 입력이 실패하면 PyAV(자체 FFmpeg 포함)로 디코딩해 배열로 넘긴다.
- 잘못하면: 시스템 FFmpeg를 sudo로 바꾸다 NVIDIA 하드웨어 디코더용 빌드를 깨면 다른 팀원·서비스까지 영향을 받는다.

## 비교
- 무슨 문제: 강의실 사진·영상을 글로 검색하기.
- 대안 1 — 이미지 분류기/태그(ImageNet 클래스, 수동 태그)로 키워드 검색: "사물함", "모니터"처럼 정해진 단어는 정확하다.
  - 이 대안을 썼다면: "학생들이 앉아 수업을 듣는 모습" 같은 문장 질의는 못 한다. 태그를 사람이 붙여야 한다.
- 대안 2 — 이미지 캡션 생성(VLM) 후 텍스트 검색: 설명이 풍부하지만 VLM을 하나 더 올려야 해서 8GB 보드에서는 메모리가 모자란다(이번에도 보드 RAM 최대 6.1GB).
- 이 방식의 약점: 넓은 장면은 허브가 된다. 점수 간격이 0.02~0.1로 좁아 임계값을 잡기 어렵다. 128차원에서는 4개 중 2개만 맞았다.
- 실무 Use Case: CCTV 영상 아카이브에서 "빨간 옷 입은 사람" 검색. 프레임 전체 대신 사람·물체 검출 후 잘라 낸 이미지를 색인하고, 시간·카메라 메타데이터로 먼저 거른다(벡터 DB의 메타데이터 필터).

## 실제로 겪은 문제 → 원인 → 해결
- 카메라 렌즈 앞에 상자 → 5장 모두 상자 면 → 사용자가 치움. 찍기 전에 한 장을 열어 확인한다.
- 보드 모니터로 미리보기 불가 → 다른 계정의 데스크톱 세션 → Tailscale 주소에만 여는 웹 미리보기.
- Safari에서 MJPEG 미리보기가 안 보임 → `<img src=/stream>`(multipart) 렌더링 문제로 추정 → `/frame.jpg`를 JS로 반복 요청.
- `{"video": 경로}` 실패 → transformers 5.20이 torchcodec 요구, torchcodec은 `libswscale.so.9` 필요(보드 FFmpeg에 없음) → PyAV 1 fps 배열.
- 1 fps 샘플링이 안 됨(151프레임 전부) → `frame.time` 기준 비교가 의도대로 동작하지 않음 → 프레임 번호 기준.

## 일부러 망가뜨려 볼 실험
1. **차원 줄이기** — 예상(원문): 128차원에서 영상 품질 약 75%. 실제: 기대 일치 768 3/4 → 256 3/4 → 128 2/4(모니터 질의가 empty_seats_로). 멀티모달은 768 또는 512를 쓴다.
2. **넓은 사진 빼기** (해 볼 것): `media/whiteboard.jpg`를 잠시 다른 폴더로 옮기고 `~/practice.sh yj ~/eg2/bin/python src/test_vision.py` — 예상: "학생들이 앉아 수업을 듣는 모습" 1위가 people로 바뀐다. 허브 하나가 결과를 얼마나 바꾸는지 보인다. (이번엔 미실행)

<details><summary>1. 개념: 텍스트 "사물함"으로 사물함 사진을 찾을 수 있는 이유는?</summary>텍스트 인코더와 비전 인코더가 같은 768차원 공간에 결과를 놓도록 함께 학습됐다. 그래서 텍스트 벡터와 이미지 벡터를 바로 내적해 비교한다(5단계 오디오와 같은 원리).</details>
<details><summary>2. 왜: 넓은 장면 사진 한 장이 여러 질의에서 1위가 되는 이유는?</summary>여러 물체가 섞인 장면은 벡터가 여러 개념의 "평균" 쪽에 놓여, 어느 질의와도 적당히 가깝다. 한 가지만 크게 찍힌 사진은 그 개념에만 가깝다. 긴 문서가 모든 키워드 검색에 걸리는 것과 같다.</details>
<details><summary>3. 트레이드오프: 장면 전체 임베딩과 물체 단위(크롭) 임베딩의 차이는?</summary>장면 전체: 색인이 단순하고 이미지당 벡터 1개. 대신 넓은 장면이 허브가 된다. 크롭: 검출기(YOLO)가 더 필요하고 이미지당 벡터가 여러 개라 인덱스가 커지지만, 물체 질의에 정확하다. 8단계가 크롭 방식이다.</details>
<details><summary>4. 장애 상황: 다른 보드에서는 되던 영상 임베딩이 이 보드에서만 ImportError가 난다. 무엇을 보나?</summary>디코더 의존성 사슬: torchcodec 설치 여부 → `ldd libtorchcodec_core*.so`로 FFmpeg 공유 라이브러리(`libswscale.so.N` 등) 누락. 보드의 FFmpeg가 NVIDIA 최소 빌드라 빠진 라이브러리가 있었다. 시스템을 바꾸지 말고 PyAV로 디코딩해 배열로 넘긴다.</details>
<details><summary>5. 내 프로젝트 적용: 강의실 CO2가 급증한 시점의 카메라 장면을 찾는 기능을 만든다면?</summary>센서 이상 시각 ±1분의 영상에서 1 fps 프레임을 뽑아 임베딩하고, "사람이 많이 모여 있는 모습" 같은 질의로 정렬한다. 넓은 장면이 허브가 되지 않게 사람 검출 후 크롭을 함께 색인하고, 원본 영상은 엣지에만 두고 벡터와 시각만 서버로 보낸다.</details>
