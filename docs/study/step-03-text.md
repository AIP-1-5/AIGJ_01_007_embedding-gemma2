# 3단계 텍스트 테스트

2026-10-23 · 결과: [docs/reports/step-03.md](../reports/step-03.md) · 앞 단계: [2단계](step-02-install.md) (인코더 선택 로드)

## 한 문장으로
한국어 질의 2개가 768/256/128 모든 차원에서 맞는 문서를 1위로 찾았지만, 질의 1의 1-2위 차이는 0.006뿐이었고 프롬프트를 빼면 오답으로 뒤집혔다.

## 세미나용 1분 설명
임베딩 검색은 문장을 768개 숫자(벡터)로 바꾸고, 질의 벡터와 가장 방향이 비슷한 문서 벡터를 찾는 겁니다. 키워드가 하나도 안 겹쳐도 됩니다. "졸리고 머리가 맑지 않다"가 "CO2가 높으면 집중력이 떨어진다"를 찾은 게 그 예입니다. LIKE 검색이나 역색인이 "같은 단어"를 찾는다면, 임베딩은 "같은 뜻"을 찾습니다. 여기서 중요한 장치가 프롬프트입니다. 질의 앞에는 `task: search result | query:`, 문서 앞에는 `title: none | text:`를 붙여서 모델에게 "이건 질문이고 저건 답 후보"라고 역할을 알려 줍니다. 이걸 빼니까 질의 1의 답이 조도 문장으로 바뀌었습니다. 또 이 모델은 앞쪽 차원에 중요한 정보를 몰아 두는 방식(Matryoshka)이라 768을 256, 128로 잘라도 순위가 대체로 유지됩니다. 인덱스 크기를 1/6로 줄이는 대신 1-2위 간격이 좁아지는 트레이드오프입니다.

## 핵심 개념

### 임베딩과 코사인 유사도
- 정의: 문장을 고정 길이 벡터로 바꾸고, 정규화한 두 벡터의 내적(= 코사인)으로 의미 유사도를 잰다.
- 비유: 역색인(Elasticsearch BM25)이 "같은 단어가 몇 번 나오나"라면, 임베딩은 "지도 위에서 얼마나 가까운가". 벡터 DB(pgvector)의 `<=>` 연산이 이것.
- 이 레포에서는: `src/test_text.py:36` — `sim = q @ dd.T` (정규화된 벡터라 내적 = 코사인).
- 잘못하면: 정규화를 빼면 긴 문서(벡터 크기가 큰 것)가 무조건 위로 온다.

### 비대칭 검색 프롬프트 (SearchQuery / Document)
- 정의: 질의와 문서에 서로 다른 접두 문구를 붙여 같은 모델이 두 역할을 구분하게 한다.
- 비유: 검색 엔진에서 질의용 분석기(analyzer)와 색인용 분석기를 따로 두는 것.
- 이 레포에서는: `src/test_text.py:25`(문서 `Document`), `src/test_text.py:31`(질의 `SearchQuery`).
- 잘못하면: 이번 실험처럼 질의 1이 조도 문장으로 뒤집힌다. 더 나쁜 경우는 색인할 때와 질의할 때 프롬프트가 달라지는 것(한쪽만 바꿈) — 기존 인덱스 전체를 다시 만들어야 한다.

### Matryoshka 차원 절단
- 정의: 앞쪽 차원일수록 중요한 정보를 담도록 학습돼, 앞 N개만 잘라 써도 된다. 자른 뒤에는 다시 정규화한다.
- 비유: 이미지 썸네일. 원본(768) 대신 작은 썸네일(128)로도 대략 알아볼 수 있다. 또는 DB에서 커버링 인덱스에 일부 컬럼만 넣는 것.
- 이 레포에서는: `src/test_text.py:34-35` — 문서 벡터를 `[:, :dim]`으로 자르고 재정규화. 질의는 `truncate_dim=dim`.
- 잘못하면: 재정규화를 빼면 코사인이 아니게 된다. 128차원은 4단계(영상·음성)에서 품질이 크게 떨어진다(원문: 약 75%).

### 최대 입력 길이와 메모리
- 정의: 트랜스포머의 attention은 입력 길이 n에 대해 n² 크기 계산·마스크를 만든다.
- 비유: 페이지네이션 없는 `SELECT *`. 결과가 커지면 서버 메모리가 먼저 터진다.
- 이 레포에서는: `src/eg2.py:27-29` — `max_seq_length`를 8192로 제한 (기본값이 1e30).
- 잘못하면: 약 14,100토큰 문서 하나로 `OutOfMemoryError: Tried to allocate 1.48 GiB`. 공용 보드에서는 남의 프로세스까지 스왑으로 밀린다.

## 비교
- 무슨 문제: 키워드가 안 겹치는 자연어 질문으로 관련 문서를 찾기.
- 대안 1 — 키워드 검색(BM25, Elasticsearch, MySQL FULLTEXT): "졸리다"와 "CO2"는 공통 단어가 없어 못 찾는다.
  - 이 대안을 썼다면: 동의어 사전을 손으로 계속 키워야 한다. 대신 "1000ppm" 같은 정확한 숫자·고유명사 검색은 BM25가 더 강하다.
- 대안 2 — LLM에 문서 전부를 넣고 묻기: 정확할 수 있지만 문서가 늘면 비용·지연이 선형으로 커지고 8GB 보드에서는 불가능하다.
- 이 방식의 약점: 비슷한 주제(CO2 vs 조도, 둘 다 "강의실 환경으로 집중이 안 됨")끼리는 점수 차가 0.006처럼 작아 쉽게 뒤집힌다. 정확한 숫자·코드 매칭에 약하다.
- 실무 Use Case: 사내 FAQ·장애 대응 문서 검색. BM25 상위 50개 + 임베딩 재정렬(하이브리드)로 숫자·에러코드와 의미 검색을 둘 다 잡는다.

## 실제로 겪은 문제 → 원인 → 해결
- (실험 중) 긴 문서에서 `OutOfMemoryError: Tried to allocate 1.48 GiB` → `max_seq_length` 기본값이 사실상 무제한 → `src/eg2.py`에서 8192로 제한.

## 일부러 망가뜨려 볼 실험
1. **프롬프트 빼기** (`python src/test_text.py --no-prompt`) — 예상: 점수 차이 정도. 실제: 질의 1 정답이 CO2 → 조도로 **뒤집힘**(0.747). 점수 분포가 전체적으로 올라가서(0.82~0.88) 절댓값 임계값도 쓸모가 없어진다.
2. **float16으로 바꾸기** — 예상(원문·CLAUDE.md): NaN. 실제: 50~2823토큰에서 **NaN 없음**, float32 대비 코사인 0.9999~1.0003으로 오히려 bfloat16(1.0003~1.0037)보다 가까웠다. 재현 조건(더 긴 입력, 비전·오디오 인코더, 다른 하드웨어)은 미확인. 규칙은 모델 권장대로 유지한다.
3. (덤) **길이 제한 없이 아주 긴 문서** — 예상: 느려짐. 실제: OOM으로 프로세스 종료.

## 회상 질문 5개
<details><summary>1. 개념: 정규화한 벡터끼리 내적이 곧 코사인 유사도인 이유와, 정규화를 빼면 생기는 일은?</summary>코사인 = 내적 / (두 벡터 길이의 곱). 길이가 1이면 분모가 1이라 내적이 곧 코사인. 빼면 벡터 크기(길이)가 점수에 섞여, 방향이 덜 비슷해도 큰 벡터가 위로 온다.</details>
<details><summary>2. 왜: 질의와 문서에 서로 다른 프롬프트를 붙이는 이유는?</summary>질문("졸려요")과 답("CO2가 높으면…")은 문장 형태가 달라서 그대로 비교하면 "비슷한 형태의 문장"끼리 가까워진다. 역할을 알려 주면 질문→답 방향의 유사도를 잰다. 이번에 빼니 질의 1이 오답으로 뒤집혔다.</details>
<details><summary>3. 트레이드오프: 768 대신 128차원을 쓰면 얻는 것과 잃는 것은?</summary>얻는 것: 저장 공간·내적 계산 1/6, 인덱스 메모리 절약. 잃는 것: 1-2위 간격(0.006 → 0.003)이 줄어 비슷한 문서끼리 뒤집히기 쉽고, 영상·음성에서는 품질이 크게 떨어진다.</details>
<details><summary>4. 장애 상황: 운영 중 어떤 문서를 색인할 때만 프로세스가 죽는다. 무엇을 의심하나?</summary>그 문서가 아주 길고 `max_seq_length`가 무제한이라 attention 메모리(길이²)가 터진 것. 이번 실험에서 약 14,100토큰에 1.48GiB 할당 OOM. 최대 길이를 자르거나 문서를 청크로 나눈다.</details>
<details><summary>5. 내 프로젝트 적용: 팀 프로젝트에서 시계열 이상 알림의 원인 문서(매뉴얼)를 찾게 하려면?</summary>매뉴얼을 문단 단위로 잘라 `Document` 프롬프트로 색인하고(pgvector 등), 알림 문구를 `SearchQuery`로 검색한다. 에러코드·센서 ID 같은 정확한 값은 BM25와 섞는다. 색인과 질의의 프롬프트·차원·모델 버전을 함께 기록해 둔다.</details>
